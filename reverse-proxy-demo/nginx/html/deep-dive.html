Reverse proxy, drawn out

Seven things a reverse proxy does for you, each one explained, drawn, and then actually executed against the running stack on this machine.

This page is inside the demo. nginx served you this HTML off its own disk. The buttons below fire real requests through that same nginx to the Spring Boot containers behind it. Current origin: -

First, the shape of the thing

A forward proxy stands in front of clients and speaks to the internet on their behalf. A reverse proxy stands in front of servers and speaks to clients on theirs. Same machinery, pointed the other way — and that reversal is the whole idea.

What is actually running right now

01 Path routing

The proxy reads the URL and picks a backend. /api/orders goes to one Java application, /api/users to a completely different one — and the browser cannot tell, because both answers arrive from the same origin.

That single-origin property is worth more than it first looks. A front end served from / can call /api/... with no CORS configuration at all, because as far as the browser is concerned nothing crossed an origin boundary.

nginx/nginx.conf 
location /api/orders { proxy_pass http://orders_backend; }
location /api/users  { proxy_pass http://users_backend;  }
Two paths, two applications

Watch servedBy: different values mean different Java processes answered.

02 Load balancing

Two containers run the identical orders image. nginx keeps them in a named pool and hands each arriving request to the next one in turn. Scaling out becomes a config line rather than an architecture project.

nginx/nginx.conf 
upstream orders_backend {
    server orders-a:8080 max_fails=1 fail_timeout=10s;
    server orders-b:8080 max_fails=1 fail_timeout=10s;
    keepalive 16;
}
Six requests to one URL

Same URL every time. The answers alternate.

03 Forwarded headers

Put a proxy in front of an app and the app immediately starts lying. The TCP connection it sees comes from nginx, so getRemoteAddr() returns nginx. The Host and scheme are nginx's too, so every redirect and generated link points at an internal address. Log an IP for rate limiting and you log the proxy, every time.

The fix is a handshake between the two halves. nginx attaches what the app can no longer see; Spring Boot's ForwardedHeaderFilter reads those headers back and rewrites the request before your controller runs. One line of YAML: server.forward-headers-strategy: framework.

nginx.conf — nginx hands it forward 
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_set_header X-Forwarded-Host  $host;
proxy_set_header X-Forwarded-Port  $server_port;
application.yml — Spring picks it up 
# users-service: corrected view
server:
  forward-headers-strategy: framework

# orders-service: raw view, for contrast
server:
  forward-headers-strategy: none
The same request, seen two ways

Load this page over https://localhost:8443 and run it again — requestURL follows the client, not the backend.

Trust boundary. These headers are just headers — a client can forge them. They are safe to believe only because nginx overwrites them at the edge. Never trust X-Forwarded-For on a server that is reachable directly.

04 TLS termination

The proxy owns the certificate, does the handshake, and forwards plain HTTP over the private network. Three Java applications and not one of them has a keystore, a cipher list, or a renewal cron job. Certificates live in exactly one place.

nginx/nginx.conf — both listeners, one server block 
listen 8080;
listen 8443 ssl;
ssl_certificate     /etc/nginx/certs/demo.crt;
ssl_certificate_key /etc/nginx/certs/demo.key;
ssl_protocols       TLSv1.2 TLSv1.3;

The certificate is self-signed and generated at startup, so your browser will warn once. In production you would also redirect HTTP to HTTPS; that line is commented out in the config so this walkthrough keeps working on both ports.

05 Caching

/api/users/slow sleeps for two seconds to imitate an expensive report. nginx is told to keep the reply for thirty seconds, so the second caller gets it instantly — and the JVM is never woken. Watch docker compose logs -f users-service: the second call logs nothing, because it never arrived.

nginx/nginx.conf 
proxy_cache users_cache;
proxy_cache_valid 200 30s;
proxy_cache_lock on;          # one request refills; the rest wait, no stampede
proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;
add_header X-Cache-Status $upstream_cache_status always;

proxy_cache_use_stale is the quiet hero there: if the backend falls over, nginx keeps serving the last good copy instead of an error page.

Two calls to a two-second endpoint

Both calls use a one-off cache key, so the first is always a real MISS (~2s) and the second a HIT (instant).

06 Rate limiting

/api/orders/limited is capped at five requests per second per client IP, with a burst of five. Fire twenty at once and roughly six get through; the rest are rejected by nginx. The Java thread pool never hears about them, which is the entire point when you are being hammered.

nginx/nginx.conf 
limit_req_zone $binary_remote_addr zone=orders_limit:10m rate=5r/s;

location /api/orders/limited {
    limit_req zone=orders_limit burst=5 nodelay;
    limit_req_status 503;
    proxy_pass http://orders_backend;
}
Twenty simultaneous requests

07 Health checks and failover

A backend that errors is pulled out of rotation for ten seconds, and the request that exposed it is quietly retried on a healthy sibling. The client sees one clean response and never learns a server died. Ten seconds later nginx tries the sick one again, so recovery needs no intervention either.

Compose plays its part at startup: nginx will not boot until all three /actuator/health checks pass, so you never get a 502 from simply racing the JVM.

Try it for real — in a terminal 
docker compose stop orders-b      # kill one replica
# now press the button below: every answer says orders-a, zero errors
docker compose start orders-b     # bring it back
# nginx re-tries a downed peer after fail_timeout (10s), so give it
# ~10s past the container going healthy, then press again: alternating returns
